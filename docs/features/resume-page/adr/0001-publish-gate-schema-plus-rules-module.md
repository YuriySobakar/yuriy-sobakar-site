# 0001 — Перевіряти публікацію під час збірки: JSON Schema для форми даних плюс модуль правил для перехресних інваріантів

- **Status:** Accepted
- **Date:** 2026-09-05
- **Deciders:** Yuriy Sobakar + SDD design (Socratic walk, depth easy)

## Context

Спека resume-page вимагає, щоб небезпечні стани resume data ніколи не доходили до живої сторінки: порожнє обов'язкове поле, більше трьох фактів, запис досвіду без результату (AC-03b, AC-07), посилання commercial project на сервіс хостингу коду (AC-05). Публікація має бути відхилена з поясненням для site owner там, де її запущено. Фундамент уже фіксує один YAML-файл із JSON Schema (`docs/adr/0002`) і правило «невалідний YAML зупиняє збірку» (карта архітектури, §Conventions). Треба вирішити, яким механізмом виражати саме ці правила.

## Decision drivers

- Спека §2 Goals: небезпечні стани не доходять до публікації; AC-07 вимагає назвати поле і правило зрозумілою мовою.
- Спека §6 NFR «Атомарність публікації»: 0 порожніх чи часткових станів на живій сторінці.
- Карта архітектури §Conventions: схема даних обов'язкова, помилка збірки замість порожньої секції.
- Розмір S, профіль Pro: мінімум коду, але без втрати читабельності помилок.

## Considered options

1. **JSON Schema для форми + окремий модуль правил на Node для перехресних інваріантів** — схема тримає обов'язкові поля, типи, `minItems`/`maxItems`; модуль `lib/resume/rules.js` перевіряє те, що схемою виражається погано (домен посилання, результат у записі, галузь у commercial project), і формулює помилку словами.
2. **Лише JSON Schema** — усі правила через `required`, `if/then`, `not` + регулярні вирази на URL; жодного власного коду.

## Decision outcome

**Chosen:** Option 1. Схема залишається простим і читабельним контрактом форми, а логіка, яка потребує слів («проєкт X: код commercial project не публікується»), живе в коді з юніт-тестами. Варіант «лише схема» відкинуто через нечитабельні повідомлення валідатора (`/projects/2/links/0 does not match pattern`), які суперечать AC-07, і через складність підтримки умовних гілок `if/then` у схемі.

## Consequences

**Positive**
- Кожне порушення має людське повідомлення з назвою запису і правилом; site owner бачить його у консолі збірки та в перевірці PR.
- Правила тестуються юніт-тестами `node --test` без збірки сайту.
- Нове правило — це функція і тест, а не переписування схеми.

**Negative**
- Правила живуть у двох місцях: форма в схемі, логіка в коді; межу треба тримати дисципліною (форма → схема, перехресне → код).
- Ще одна залежність для валідації схеми на етапі збірки (уже передбачена `docs/adr/0002`).

**Neutral**
- Перенести окреме правило зі схеми в код або навпаки — локальна зміна з тестом, без міграції даних.
